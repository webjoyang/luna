# 0003 — 销售合同明细作为合同聚合的一部分整体保存，不设独立 Controller

## 状态

accepted

## 上下文与决定

`SalesContractItem`（销售合同明细）没有自己的 Controller / 权限码。明细写操作全部嵌在合同保存载荷里：`SalesContractSaveReqVO.items` 携带整份明细列表，服务端在一个事务内对主表 insert/update、对子表按 `contract_id` 先删后插；删除合同时明细随主表一起逻辑删除。明细的读取通过 `SalesContractRespVO.items` 嵌套返回。

这与 ADR-0002（客户联系人独立 Controller）是**刻意相反**的选择。

## 理由

两类子资源形态相似（都是"主表 + 多行子表"），但使用形态不同：

1. **生命周期完全从属**：明细行不能脱离合同存在，也没有"只改一行数量、不动其他行"的独立业务动作——用户在整页合同表单里编辑明细表格，一次保存提交整表，整体替换与 UI 行为天然同构。联系人则是业务运行中持续对单行增删改（见 ADR-0002）。
2. **金额一致性要求**：合同 `totalQuantity` / `totalAmount` 必须由全部明细权威重算（行金额 = 数量 × 单价 + 其他费用）。整表替换 + 事务内重算保证汇总与明细永远一致，避免多行独立写导致的中间态偏差。
3. **无独立分权需求**：能建/改合同就能改其明细，独立权限码没有业务场景。
4. **允许零明细**：合同可先建档后补明细，明细 0~N 行，整体保存语义自然覆盖。

## 考虑过的备选

- **与联系人一致，独立 Controller（`sales-contract-item` 端点逐行增删改）**：权限与结构更"规整"，但与整页表单交互不符，且金额汇总需要在每次行操作后重算主表，事务边界更碎。
- **沿用旧系统做法（明细序列化为 JSON 字符串存主表列）**：开发最快，但明细不可查询、不可约束、无法与未来发货/开票链路按行关联，技术债在第一版就埋下。

## 后果

- 前端编辑页需维护完整明细数组并整体提交；后端保存接口体积随行数增长（合同行数量级为几十行，可接受）。
- 并发编辑同一合同时后保存者整体覆盖先保存者的明细修改；MVP 不做乐观锁，后续如有并发诉求再补版本号。
- 未来若出现"合同行级发货/开票/交期"等独立子资源，它们关联 `item_id`，但明细本身的写入口仍保持聚合保存，不拆独立端点。
