# 0005 — 供应商编号全量唯一：基础档案采用单据级编号规则

## 状态

accepted

## 上下文与决定

供应商是基础档案，却与无编号的客户档案不同，拥有租户内唯一编号 `supplierNo`，形如 `SUP20260001`（`SUP` + 年份 + 4 位顺序号，超 9999 自然扩位）。编号规则与合同编号（ADR-0004）完全同构：

- 普通唯一索引 `UNIQUE (tenant_id, supplier_no)`，**不带** `WHERE deleted = 0`：软删不释放编号；
- 取号（当前年份最大数字后缀 +1）与手填号查重的扫描范围**包含已删除行**，绕过 MyBatis-Plus 逻辑删除自动过滤；
- 新建缺省服务端自动生成，也允许手填（撞号报 `1-030-005-001`，不区分目标是否已删除）；
- 提供只读、不占号的"预览下一个编号"接口；
- 不引入数据库序列/Redis，沿用 product/销售合同已验证的数字后缀扫描取号。

## 理由

1. 旧系统（linaagi）供应商已有 `SUP-` 编号，并被入库（StockIn）、付款申请（PaymentRequest）等业务环节引用。供应商是后续采购入库单、付款凭据上的往来主体，编号会出现在对账等对外/半对外场景，审计属性同单据，而非纯内部主数据。
2. 方案评审时在"无编号（对齐客户）/ 自动编号 / 手填编号"之间明确选择"自动生成 + 可手填"，唯一性口径与合同一致（软删不重用），直接复用已验证的取号实现。

## 考虑过的备选

- **无编号（客户档案现状）**：最省，但从旧系统迁移供应商时无号可对，未来单据只能用 ID 或公司名引用，公司重名时无法消歧。
- **部分唯一索引 `WHERE deleted = 0`（product 模块现状）**：编号池可重用、与产品一致；但产品编号是内部主数据，供应商编号承担往来对账的审计职能，语义更接近合同编号，一致性让位于审计安全。

## 后果

- 取号与查重 Mapper 方法需显式包含 `deleted = 1` 的行，实现处注释标明意图，防止被当疏漏"修复"（同 ADR-0004 后果）。
- 客户档案保持无编号、产品编号保持部分唯一：两者与供应商的差异都是刻意的，不应"顺手对齐"。
- 大量删除会造成顺序号空洞，可接受。
