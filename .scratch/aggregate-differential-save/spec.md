# 阶段一：聚合子表按行 ID 差异保存改造（七个既有聚合统一取代"先删后插"）

Status: ready-for-agent

## Problem Statement

Luna ERP 七个"主表 + 聚合子表"业务单据，更新主表时对子表的持久化全部采用"按父 ID 逻辑删除全部旧行 + 批量插入本次提交行"（ADR-0003 确立的机制）：销售合同明细、染色颜色明细、胚布单颜色分配、纱线采购明细、发货明细与卷清单、入库明细与库位放置、纱线配比 BOM 明细。

这带来一个正在兑现的实际问题：**聚合子表的行 ID 每次保存都全部换一批**。从开发者视角：

1. 外部模块无法用子表行 ID 建立稳定关联——进度反馈覆盖层（ADR-0031）需要挂到染色颜色行上，但染色单每保存一次颜色行 ID 就全变，关联必然悬挂。合同行级发货/开票等未来需求（ADR-0003 已预见）也会撞上同一堵墙。
2. 行的审计字段（creator/create_time）每次保存被整体刷新，无法回答"这行最初是谁何时录的"。
3. 前端编辑表格无法用稳定行 ID 作 key 与局部交互身份，只能依赖数组下标。
4. 逻辑删除表中堆积大量"内容未变却反复删插"的行尸。

业务侧需要先完成这次纯工程治理（不改变任何业务语义、不夹带新功能），为进度反馈 MVP 提供稳定的行身份，同时统一七个模块的持久化约定，避免未来逐模块打补丁。

## Solution

在 luna-srv `lunasrv-module-lunaerp` 内，把七个聚合的子表保存机制统一改为**按行 ID 差异保存（differential save）**，聚合边界（无独立 Controller/权限码、整表载荷提交、同事务、随主表级联删除、汇总服务端重算）全部保持不变。

差异规则（同事务内）：

- 提交行带 `id` 且该 id 属于当前父表/父行的库内存量 → `updateById`
- 提交行无 `id` → insert
- 库内存量中存在、但本次提交未携带的 id → 逻辑删除（沿用 `deleted=1`）
- 有序号的子表，每次保存按提交顺序统一重排行号

两级子表（发货：明细→卷清单；入库：明细→库位放置）按"先差异保存父行、再差异保存子行"的顺序处理，未变更父行的 id 保持不变；提交中子行引用了本次被删除父行 id 时，service 层报校验错误（防御性）。

跨聚合引用守卫：染色单更新时，被移除的颜色行下若存在反馈缸（阶段二表，本阶段先预留扩展点；若阶段二尚未建表，此守卫在阶段二落地时补齐——见 Further Notes），硬拦截报错。

四个当前 SaveReqVO 缺少 `id` 的子表（合同明细、染色颜色、胚布颜色、配比 BOM 明细）补可空 `id` 字段；七个模块的前端编辑页联动改为：加载详情后保留每行后端 id，以行 id（而非数组下标）为编辑身份，提交时原样回传。

验收锚点：**编辑保存后，未被改动的子表行 id 必须保持不变**。

## User Stories

### 销售合同（SalesContractItem）

1. 作为后端系统，我想在更新销售合同时对合同明细做差异保存：带 id 且属于本合同的行走 update，无 id 的行走 insert，本合同库内有但本次未提交的行走逻辑删除，以便明细行身份在多次编辑间保持稳定。
2. 作为业务员，我想编辑销售合同时只改一行数量，保存后其余明细行仍然是原来的数据库行（id、创建人、创建时间不变），以便行级追溯信息不被刷新。
3. 作为业务员，我想在明细表格中新增一行、删除另一行后保存，新增行落库、被删行逻辑删除、其余行不变，交互结果与"整体替换"时代完全一致。
4. 作为业务员，我想把明细行顺序调整后保存，服务端按提交顺序重排行号（如合同明细有行号概念时），金额合计与数量汇总仍由服务端按最新明细权威重算。
5. 作为业务员，我想删除销售合同时其全部明细仍随主表级联逻辑删除，行为与改造前一致。
6. 作为前端用户，我想合同编辑页加载已存明细时每行持有后端 id，编辑过程中行不丢 id，提交载荷原样回传 id。

### 染色单（DyeingColor）

7. 作为后端系统，我想在更新染色单时对颜色明细做差异保存（update/insert/逻辑删除三分流），以便染色颜色行获得跨多次编辑稳定的 id，供进度反馈覆盖层稳定关联。
8. 作为业务员，我想修改某个颜色行的数量/匹数/投染数后保存，该行走 update 而不是删旧插新，行 id 不变。
9. 作为业务员，我想在染色单中新增一个颜色、删除一个颜色、保留其余颜色后一次保存，三类行分别落为 insert/逻辑删除/update。
10. 作为业务员，我想保存染色单时行号按提交顺序重排（当前实现按数组下标赋 lineNo），从 1 连续编号。
11. 作为业务员，我想删除染色单时其全部颜色行仍随主表级联逻辑删除。
12. 作为前端用户，我想染色单整页编辑加载颜色明细时保留每行后端 id 并随保存回传。
13. 作为系统，我想当阶段二进度反馈上线后，染色单更新试图移除一个其下存在反馈缸的颜色行时，service 层硬拦截报错（错误码 1-030-017-004），提示先删除该颜色的缸反馈（本阶段预留调用点，阶段二补全实现）。

### 胚布单（GreigeOrderColor）

14. 作为后端系统，我想在更新胚布单时对颜色投胚分配做差异保存三分流。
15. 作为业务员，我想只调整某颜色的成品下单量/损耗/投胚需求时，该行 update、其余行 id 不变。
16. 作为业务员，我想增删颜色行后保存，insert 与逻辑删除各归其位；胚布单删除时颜色分配仍级联逻辑删除。
17. 作为前端用户，我想胚布单编辑页颜色表格以行 id 为身份加载与回传。

### 纱线采购单（YarnOrderItem）

18. 作为后端系统，我想在更新纱线采购单时对采购明细做差异保存三分流；该子表 SaveReqVO 已有 id 字段（历史上更新时被无视），本次让其真正生效。
19. 作为业务员，我想改一行实采量/单价后保存，该行 update、金额仍服务端重算，其余行 id 不变。
20. 作为业务员，我想增删采购明细行后保存行为正确；该子表无行号字段，不做行号重排。
21. 作为前端用户，我想纱线采购单编辑页提交明细时回传每行 id（当前前端未保证）。
22. 作为业务员，我想删除纱线采购单时明细仍级联逻辑删除。

### 发货单（ShipmentItem + ShipmentRoll）

23. 作为后端系统，我想在更新发货单时先对发货明细差异保存、再对卷清单差异保存，保证未变更明细行 id 不变，从而挂在其下的卷清单关联不悬空。
24. 作为仓管员，我想修改某明细行数量后保存，明细行 update、其下卷记录全部原样保留（卷 id 不变）。
25. 作为仓管员，我想删除一条明细行时，其下卷清单一并逻辑删除；其他明细行与其卷清单不受影响。
26. 作为后端系统，我想当某次提交中卷记录携带的 shipmentItemId 指向本次被删除的明细行 id 时，返回校验错误（防御性，正常前端操作不可达）。
27. 作为仓管员，我想在保留明细行的前提下增删改卷记录，卷记录各自走 insert/update/逻辑删除。
28. 作为前端用户，我想发货工作台明细表格与卷清单弹窗均以行 id 为身份加载与回传（当前以数组下标维护）。
29. 作为业务员，我想删除发货单时明细与卷清单仍级联逻辑删除；仅草稿态可改可删的守卫不变。

### 入库单（StockInItem + StockInItemPlacement）

30. 作为后端系统，我想在更新入库单时先差异保存入库明细、再差异保存库位放置，未变更明细行 id 不变，放置关联不悬空。
31. 作为仓管员，我想修改某条入库明细后保存，明细 update、其下放置记录全部保留。
32. 作为仓管员，我想删除明细行时其下库位放置一并逻辑删除；其他行不受影响。
33. 作为后端系统，我想放置记录引用本次被删明细行 id 时返回校验错误（防御性）。
34. 作为仓管员，我想在保留明细行的前提下增删改放置记录（库位、匹数、数量、备注），各走 insert/update/逻辑删除。
35. 作为前端用户，我想入库工作台明细与放置弹窗以行 id 为身份加载与回传。
36. 作为仓管员，我想入库单删除时明细与放置仍级联逻辑删除；草稿/已审核/已取消的状态守卫与过账红冲逻辑完全不变。

### 纱线配比 BOM（YarnRecipeBomItem）

37. 作为后端系统，我想在更新配比 BOM 时对配比明细做差异保存三分流。
38. 作为业务员，我想改某纱线行的配比百分比/备注后保存，该行 update、其余行 id 不变；删除 BOM 时明细仍级联逻辑删除。
39. 作为前端用户，我想配比 BOM 编辑页明细行携带并回传 id。

### 通用质量与回归

40. 作为开发者，我想所有差异计算只依赖"库内存量 id 集"与"本次提交 id 集"，逻辑删除沿用 MyBatis-Plus 软删除机制，不引入物理删除、不建数据库外键。
41. 作为开发者，我想差异保存在原保存方法的同一事务内完成，主表更新与子表差异提交同成功同失败，与改造前事务边界一致。
42. 作为开发者，我想前端漏改或未回传 id 时，旧行不会被误删为"无法匹配"以外的危险状态——未携带 id 的行一律按新增处理、未提交的存量行按删除处理（即行为退化为"全删全插"但不报错），因此"未改行 id 不变"是各模块回归验收的硬锚点。
43. 作为开发者，我想产品图片（ProductImage）等无外部引用的纯附件子表**不在本次改造范围**，保持现状。
44. 作为开发者，我想本次改造不改变任何接口路径、权限码、菜单、字典与业务校验规则，前端页面除行身份处理外无交互变化。

## Implementation Decisions

- **模块与包**：全部在 `lunasrv-module-lunaerp`，不新增模块、不新增包；改动七个已有 ServiceImpl 及其子表 Mapper/SaveReqVO。
- **涉及聚合（7 个，子表 9 张）**：
  - business.salescontract → SalesContractItem
  - production.dyeingorder → DyeingColor
  - production.greigeorder → GreigeOrderColor
  - production.yarnorder → YarnOrderItem
  - business.shipment → ShipmentItem、ShipmentRoll
  - stock.stockin → StockInItem、StockInItemPlacement
  - production.yarnrecipebom → YarnRecipeBomItem
- **VO 变更**：四个子表 SaveReqVO（SalesContractItemSaveReqVO、DyeingColorSaveReqVO、GreigeOrderColorSaveReqVO、YarnRecipeBomItemSaveReqVO）补可空 `id`（更新时携带、新增时为空）；其余子表 VO 已有 id，无需改结构。RespVO 已含 id 的保持不变，未含 id 的按需补（至少保证前端编辑回传链路所需）。
- **Mapper 支撑**：每个子表 Mapper 提供"按父 id 查库内存量（含 id）"与"按 id 批量逻辑删除"能力（多数已有 selectByXxxId + 通用 deleteByIds；缺失的补齐，如 selectIdsByXxxId 视实现需要）。卷清单/放置另需按父行 id 集合查询存量以做两级差异。
- **Service 差异算法（统一模式，各模块内联实现，本期不抽公共框架类）**：取库内存量行 → 以 id 建索引 → 遍历提交行：id 非空且命中存量则 updateById 并重标命中、未命中 id（非法 id 视为新增还是报错：统一按"id 不属于本父则报错"处理，防止跨父 id 串数据）、id 为空则 insert → 未命中的存量 id 批量逻辑删除 → 重排行号（仅有序号子表）。两级子表严格先父后子。
- **染色单守卫扩展点**：DyeingOrderServiceImpl 差异计算得出"待删除颜色行 id 集"后，预留 `progressVatMapper.countByColorIds(...)` 类调用点；阶段二建表前以接口隔离或注释占位，阶段二启用，命中即抛 1-030-017-004。实现阶段若阶段二尚未开发，先写 TODO 锚点并在 PR 说明，禁止提前建表。
- **前端联动（7 个编辑页）**：sales-contract、dyeing-order、greige-order、yarn-order、shipment（明细 + 卷弹窗）、stock-in（明细 + 放置弹窗）、yarn-recipe-bom。详情数据加载后明细行保留 `id`；el-table row-key 设为行 id；提交 payload 中未删行携带原 id；新增行 id 留空。不改页面布局、字段与交互文案。
- **不做的事**：不抽公共差异保存基类/工具（七处内联重复可接受，避免过早抽象；待第三处以上非聚合场景需要再提）；不引入乐观锁与版本号（ADR-0003 已明确 MVP 不处理并发覆盖）；不改 SQL DDL（行 id 列早已存在）。
- **ADR/CONTEXT**：遵循 ADR-0032；ADR-0003 已补注；GLOSSARY.md 术语中"随单聚合保存、级联删除"的表述语义不变（聚合边界未动），无需再改。
- **错误码**：本阶段不新增错误码。染色单守卫错误码 1-030-017-004 在阶段二定义；防御性的"子行引用了被删父行"优先返回通用参数校验错误，不占用专属码。

## Testing Decisions

- **唯一测试接缝**：ServiceImpl 层 Mockito 单测（JUnit5 + Mockito，不起 Spring 上下文、不连数据库），与全项目 30 个现有测试类同一接缝，不新增测试类型、不引入集成测试。
- **扩展 7 个已有测试类**（不新建测试类）：SalesContractServiceImplTest、DyeingOrderServiceImplTest、GreigeOrderServiceImplTest、YarnOrderServiceImplTest、ShipmentServiceImplTest、StockInServiceImplTest、YarnRecipeBomServiceImplTest。
- **每个模块必测的四条更新路径（外部行为断言，不绑定内部实现）**：
  1. 全部行原样提交 → 每张子表只有 update 调用（或明确允许无调用）、零逻辑删除、零 insert，返回详情中 id 集与库内一致；
  2. 修改一行字段 → 该行被 update 且携带新值，未改行不被删除/新增；
  3. 移除一行 → 恰有该行 id 被逻辑删除，其余行 id 不变；
  4. 新增一行 → 恰有一次 insert，存量行 id 不变。
- **两级子表追加用例**（发货、入库）：删父行时其子行随之逻辑删除；子行 payload 引用被删父行 id 时报错；保留父行时子行独立增删改不影响父行。
- **染色单追加用例**：待删颜色行 id 集被正确计算（用 mock 验证守卫扩展点被调用；阶段二表未建前断言扩展点预留行为不影响保存）；跨父非法 id 提交报错。
- **回归断言**：主表汇总重算（合同金额、胚布投胚、采购金额、发货合计）在差异保存后仍按最新子表重算；删除主表仍级联删子表。
- **前端无自动化测试**（仓库无前端测试设施）：以人工回归清单作为验收标准，七页各走一遍"加载→改行→加行→删行→调序→保存→重开校验 id 与内容"，重点验证"未改行不串、关联数据不丢"（发货卷清单、入库放置归属正确）。
- **好测试标准**：只断言可观察行为（最终哪些行 insert/update/逻辑删除、返回数据与汇总值、错误码），不断言私有方法调用次序等实现细节；mock 只用于 Mapper 协作者。

## Out of Scope

- 进度反馈功能本身（反馈缸/反馈记录/缸卡墙，见阶段二 spec）。
- 新建公共差异保存框架/注解/基类；乐观锁、并发编辑合并、变更审计日志。
- ProductImage 及未来任何纯附件子表的改造。
- 聚合边界调整：不拆任何独立子资源端点、不加权限码、不改接口路径与 DTO 的业务字段。
- 数据库外键、唯一约束等 DDL 变更。
- 后端接口契约版本化与历史数据迁移脚本（旧数据行 id 已存在，逻辑删除行无需处理）。
- 前端视觉/交互改版，仅做行身份联动。
