# 0009 — 染色单无业务编号，不设 order_no 字段

## 状态

accepted

## 上下文与决定

染色单主表 `lunaerp_production_dyeing_order` **不设**业务编号字段（无 `order_no` / `dyeing_order_no` 等），后端不提供 `get-next-no` 预览编号接口。这与项目内所有其他单据刻意不同：销售合同有 `contract_no`（CH+年+4位）、胚布单有 `order_no`（PB+月日+3位）、供应商有 `supplier_no`（SUP+年+4位）。

染色单的对外标识使用数据库自增 `id`（int8）和关联的 `contract_no`（合同号快照）共同定位。

## 理由

1. **染色单是内部生产指令，非对外签约/对账凭证**：合同号是对外契约编号（CH...）、胚布单号是下达给坯布厂的厂内票据编号（PB...）、供应商号是往来主体档案编号。染色单在参考项目（linaagi）中本就无业务编号，仅用自增 id，业务方已习惯通过"客户+合同号+日期"定位染色单，不需要独立编号。
2. **避免编号体系膨胀**：每个单据类型都分配一个编号前缀（CH/PB/SUP/...）会让编号体系越来越复杂，用户需要记忆多种前缀规则。染色单作为内部高频单据，不引入新前缀降低认知负担。
3. **无编号唯一性约束需求**：合同号/胚布单号需要租户内唯一且不重用（软删不释放），是因为它们是对外凭证。染色单无此需求，省去唯一索引与取号逻辑的实现与维护成本。

## 考虑过的备选

- **沿用编号规则，设 `dyeing_order_no`（如 RS+年+4位 或 DY+月日+3位）**：与其他单据一致，列表展示有独立编号列。但染色单内部流转不依赖编号，且参考项目已验证无编号可行；引入编号只是"为了一致而一致"，无实际业务价值，反而增加取号/查重/唯一索引的维护成本。
- **用合同号+行号组合作为业务标识**：一张合同可能对应多张染色单，组合号不直观且长度不可控。不采用。

## 后果

- 列表页不展示"染色单号"列，定位单据靠"合同号+客户+日期+承染方"组合。
- 后端无需实现编号生成与查重逻辑，Mapper 无需唯一索引（除主键外）。
- 未来若业务方要求染色单有独立编号（如对接染厂系统需要），可在后续版本追加 `order_no` 字段与取号逻辑，存量数据回填即可，不影响现有结构。
- 全系统出现"有编号"与"无编号"两类单据，CONTEXT.md 已显式记录该刻意不一致，未来工程师看到染色单无 order_no，**不应**"补上"编号字段。
