# 0004 — 销售合同编号全量唯一：软删不释放编号，取号扫描含已删除行

## 状态

accepted

## 上下文与决定

合同编号 `contractNo` 形如 `CH20260001`（`CH` + 年份 + 4 位顺序号，超 9999 自然扩位），租户内唯一。唯一性用**普通唯一索引** `UNIQUE (tenant_id, contract_no)` 实现，**不带 `WHERE deleted = 0` 条件**：合同逻辑删除后编号仍被占用，不会重新分配给新合同。取号（找当前年份最大顺序号 +1）与手填号查重的扫描范围都**包含已删除行**，因此需要绕过 MyBatis-Plus 的逻辑删除自动过滤（自定义查询）。

## 理由

1. **业务单据编号的审计属性**：合同是对外业务单据，编号可能出现在纸质打印件、聊天记录、客户邮件中。软删只是系统内不可见，若编号被新合同重用，外部沟通中"CH20260001"将指向两份不同合同，审计与对账无法区分。产品编号是内部主数据，重用无此外部风险。
2. **用户明确决策**：编号方案评审时在"部分唯一索引（软删可重用）"与"全量唯一（软删不重用）"之间明确选择后者。
3. **实现简单**：普通唯一索引对软删/恢复（未来若支持）天然友好，无需像部分索引那样处理"恢复时撞号"。

## 考虑过的备选

- **部分唯一索引 `WHERE deleted = 0`（product 模块现状）**：编号池不浪费，且与产品模块一致。但产品编号是内部主数据、合同编号是对外单据标识，业务语义不同；一致性让位于审计安全。未来工程师看到本索引与 product 不同，**不应**将其"修正"为部分索引。
- **数据库序列 / Redis 计数取号**：旧系统用"取最大号字符串排序"曾产生排序错误（`CH9` > `CH10`），product 模块已改为数字后缀比较的扫描取号。序列/Redis 引入跨租户/跨年重置的额外复杂度，沿用 product 已验证的扫描方案（租户内按前缀、数字后缀取 max）即可。

## 后果

- 取号与查重 Mapper 方法需显式包含 `deleted = 1` 的行（绕过逻辑删除过滤），实现时需注释说明意图，防止被当疏漏"修复"。
- 手填编号与已删除合同撞号时，同样报 `1_030_003_001`（合同编号重复），不区分目标是否已删除。
- 顺序号只增不减，大量删除会造成序号空洞——对业务单据可接受。
