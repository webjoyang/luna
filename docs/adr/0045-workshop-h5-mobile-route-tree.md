# ADR-0045：车间移动 H5 与客户门户同栖 luna-ui——独立移动路由树，按交互复杂度分化组件库

**状态**：Accepted
**日期**：2026-10-07
**关联**：wayfinder 15-workshop-h5 grilling（Q4/Q5/Q6）；ADR-0044（客户门户，其后果第 3 条点名本决策）；spec `.scratch/workshop-h5/spec.md`；04 号打印契约（`luna.h5.base-url`、布票二维码 `/h5/scan/weaving-ticket?code=`）

## 背景

W4 同时落两个移动端：14 号客户门户（外部客户免登、4–6 个只读+确认页）与 15 号车间 H5（内部员工登录、扫码报工/卷级质检/移动发纱，含拍照、弱网重试、PDA 与 WebView 多终端）。两者都要回答：是否独立工程、用什么前端形态、挂哪个鉴权域。

三条已查清的事实：

1. 冻结的布票二维码是**同源路径形态** `{luna.h5.base-url}/h5/scan/weaving-ticket?code=`（04 号契约）；工人身份是 `system_users` 员工，芋道 admin 鉴权/RBAC/租户/操作日志可整套复用。
2. luna-ui 已有独立于菜单的常量路由（`src/router/modules/remaining.ts`）与路由白名单机制（`src/permission.ts`），挂载免菜单路由区无需改框架；Vite 路由级懒加载与 manualChunks 可把移动依赖隔离出 PC 首屏。
3. luna-ui 当前没有任何移动交互依赖（`qrcode` 仅生成、无摄像头扫码、无移动组件库）；ElementPlus 是桌面组件，触摸尺寸/底部 Tab/拍照上传/弱网反馈均不适配手机现场。

## 决策

1. **车间 H5 栖身 luna-ui 单工程，独立 `/h5/**` 路由树**：自带 H5Layout（Vant Tabbar），不嵌 PC 菜单框架；全部路由懒加载，Vant 与 html5-qrcode 独立 chunk；移动子树禁止引用 PC 业务组件。与 14 号门户 `/portal/**` 同一工程落点，互相同构。
2. **组件库按交互复杂度分化**：车间 H5 引入 **Vant 4**（Tabbar/Toast/Dialog/Uploader 等移动组件）+ **html5-qrcode**（二维码与 Code128 摄像头扫码，不可用时降级）；客户门户保持零新依赖（ElementPlus+自定义 CSS，max-width 480px）。两条移动路由树的组件依赖互不污染。
3. **鉴权域与门户刻意不同**：H5 端点走 `/admin-api/lunaerp/h5/workshop/**` 标准员工 token（账号密码登录、与 PC 同源共享 token）；门户走 `/app-api/lunaerp/portal/**` + 自研门户令牌 Filter（ADR-0044）。**共享工程模式，不共享凭证机制**。
4. **键盘楔入为一等公民**：每个扫码页常驻自动聚焦输入框+回车触发（PDA 头扫/USB 扫码枪路径），摄像头仅为 HTTPS/localhost 安全上下文下的增强路径；`http://192.168.*` 车间局域网降级为纯楔入，不因 getUserMedia 被禁而阻断业务。
5. **接入层独立、业务规则零复制**：新增 `lunaerp.h5.workshop` 接入包做登录人范围过滤、扫码编排（含胚布自动交接）、H5 VO 裁剪与发纱幂等包装；所有写库经既有生产域 Service（布票状态机、检验明细、领纱发纱），H5 层不持有任何业务状态机。

## 理由

1. **单工程匹配私有化买断的交付形态**：一期客户买的是一套系统、一个构建产物、一个域名/证书；独立 H5 工程会带来第二套 CI/部署/域名/类型与请求层复制，而页面体量（约 9 页）远撑不起这份长期成本。路由树+chunk 隔离已能拿到"独立工程"的主要收益（PC 首屏不膨胀、依赖方向可控）。
2. **与门户同构降低组织成本**：两个移动端共享构建链、请求层、token 存储与发版节奏；未来第二个移动场景有现成骨架。若分属两个工程，每次底座升级（axios/鉴权/字典）都要双改。
3. **组件库分化是真实取舍而非一致性破坏**：门户页面是静态信息展示与两个表单，桌面组件库+少量 CSS 足够，新依赖零收益；车间 H5 的核心交互（扫码、拍照压缩、底部 Tab、现场级 Toast/防连点、弱网草稿）在 ElementPlus 上自造等于重写半个移动组件库，且触摸可用性风险高。差异化的判定标准是"交互复杂度"，不是"移动端必须统一技术栈"。
4. **admin/app-api 不混用**：工人是员工，账号开通、角色授权、租户隔离、操作审计全部归芋道既有体系；为 H5 另造令牌或把员工端点塞进 app-api 都会制造第二套身份面。与门户的差异来自使用者本质不同（内部员工 vs 外部客户），而非技术偏好。
5. **现场网络与设备不可选**：车间 HTTP 局域网与廉价 PDA 是主流现实，getUserMedia 的 HTTPS 硬约束无法靠代码绕过；把键盘楔入做为主路径、摄像头作为增强，是让系统在最差终端上仍可用的唯一选择。

## 考虑过的备选

- **独立 Vite H5 工程（独立部署/域名）**：边界最"干净"，但双构建链、类型/请求层抽包或复制、双域证书与 CORS、发版双倍操作；一期页面量与私有化交付形态下收益不成立。否决。
- **不引 Vant，ElementPlus+自定义 CSS 硬适配**（门户方案照搬）：门户只读轻交互可行，车间场景需要自造 Tabbar/上传/触摸反馈/键盘弹层适配，成本与可用性风险均高。否决，但该方案保留给未来的轻量移动页。
- **H5 挂 `/app-api` 与门户共用免登 Filter 思路**：工人不是外部会员，免登令牌模型与"挡车工只看自己机台任务"的强身份要求冲突；复用 admin 鉴权零开发且审计完备。否决。
- **摄像头扫码为唯一入口**：在 HTTP 车间网与无摄像头 PDA 上直接不可用。否决，降级为楔入优先。
- **企微/钉钉 OAuth 免登一期接入**：各私有化客户 corp 凭证/可见范围配置不同，交付成本高且账号仍需在系统开通；一期统一账号密码，免登列二期。

## 后果

- luna-ui 增加 Vant/html5-qrcode 依赖与 VantResolver 构建配置；PC bundle 通过独立 chunk 与懒加载保持首屏零增量，构建产物体积增大（移动 chunk 仅在访问 /h5 时加载）。
- 两套移动布局（PortalLayout/H5Layout）并存，后人需按"外部客户轻展示→门户模式；内部现场重交互→H5 模式"选择，本 ADR 提供判定依据。
- 工人必须记住账号密码（或由浏览器/WebView 记住）；企微/钉钉内打开不是一键免登，二期接入 OAuth 时仅替换登录页与 token 获取层，路由树与端点不变。
- 摄像头能力依赖部署侧提供 HTTPS；纯 HTTP 站点只能走 PDA/扫码枪，部署文档须显式声明该限制。
- 14 号门户与本票的工程模式互相引用；如未来出现第三个移动触点，默认沿用"单工程内独立路由树"，组件库按交互复杂度单独立论。
