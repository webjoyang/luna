# ADR-0021：挡车工复用 system_users + system_post 岗位，不新建员工表

**状态**：Accepted
**日期**：2026-09-25
**关联**：生产管理-质检确认 MVP

## 背景

责任认定为 `OPERATOR` 时必须指认具体挡车工——他是工资扣款的主体。新项目现状：

- lunaerp 没有 HR/员工主数据，也没有机台（织机）主数据与机台任务实体；
- 参考系统靠"入库明细机台号 → 机台当前任务 → 任务上的挡车工"反查责任人，这条解析链在新项目完全不存在；
- system 域有 yudao 自带的 `system_users`（用户）+ `system_post`（岗位）+ `system_user_post`（用户岗位关联），前端有现成的人员选择组件；销售合同的业务员已开"业务字段关联 system User"先例（`salespersonUserId`，CONTEXT.md 业务员条）。

用户决策：挡车工就是"员工（人员）表里岗位为挡车工的那批人"，人员与系统账号共用同一套表，不为本功能新建员工表。

## 决策

- 在 `system_post` 中 seed 一条**"挡车工"岗位**；挡车工 = 关联该岗位的 `system_users` 用户。
- 质检确认表存 `workerUserId`（逻辑关联，不建外键）+ `workerName`（姓名快照，用户改名不回写历史记录），与业务员 `salespersonUserId` 模式同构。
- 前端认定对话框复用现有 `UserSelect` 组件并按挡车工岗位过滤候选。
- 自动生成时无法反查挡车工（无机台/任务数据源），**由认定人在确认时选择**：责任为 OPERATOR 时必填，EQUIPMENT / WAIVED 可空。

## 后果

- 挡车工需要拥有系统账号才能被选中——在本系统里"账号名册"即兼作"员工名册"，这是用户接受的前提。
- 工资扣款汇总按 `workerUserId` 聚合，不存在参考系统中"挡车工未识别"的未分配桶（旧系统机台反查失败才会出现该桶）。
- 若未来建设独立 HR 员工模块，再评估挡车工字段向员工实体迁移；历史行因保留了姓名快照且 userId 稳定，迁移不影响存量数据可读性。
