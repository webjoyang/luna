# ADR-0034：生产进度为合同锚点的只读聚合视图，join 反查流水、实时批量聚合

**状态**：Accepted
**日期**：2026-09-28
**关联**：生产管理-生产进度；ADR-0033（发染记录）、ADR-0017（通用库存流水）、ADR-0031（进度反馈）、ADR-0029（发货过账）

## 背景

旧系统订单进度（OrderProgress）靠手动填进度字符串，跨合同看板由前端 `useContractProgress` 拉 3 个接口、按合同号/产品文本匹配聚合，数据孤岛与口径漂移是结构性缺陷。新系统已删除订单实体，需要回答：去掉订单后全链路进度怎么跟踪。候选方案之一是给库存流水表加 `sales_contract_id` 列以便"合同侧直查流水"，但这是 schema 变更且需回填历史。

## 决策

### 1. 只读聚合视图，不是表、不是另一张单

进度 = 合同下各生产单据状态的**投影**：`ProductionProgressView` 由 `ProductionProgressQueryService` 实时聚合（DTO 不落库），合同（SalesContract）是唯一锚点，合同侧不加任何进度字段（根除旧系统手动字符串）。暴露两个接口：`page`（跨合同列表，含各环节关键量+预警数）与 `get`（单合同全链路视图）。消费方为本期"生产管理 → 生产进度"独立菜单页（列表+单合同抽屉）；合同工作台"生产进度"页签与跨合同看板 widget 后置，复用同一服务。

### 2. join 反查流水，不给 ledger 加列

`lunaerp_stock_ledger` **不加** `sales_contract_id` 列：入库/发货量按 `related_doc_type + related_doc_id` join 入库单/发货单取 `sales_contract_id`；发染量从发染记录表经胚布单聚合（ADR-0033）。代价是查询多一层 join，换来零 schema 迁移、零历史回填；流水表保持"通用凭证"定位，不为某一消费方加维度列。

### 3. 口径

- **单位**：进度只聚合 KG（合同/明细单位 KG/M 字典）；M 单位明细原样展示、不进合计，不做克重折算。
- **取消单**：一律排除 CANCELLED——已取消合同不进默认列表；各环节只统计非取消单据的数量。
- **胚布/成品入库区分**：按入库单 `greigeOrderId` 非空=胚布入库、`dyeingOrderId` 非空=成品入库；约定两者不同时填、**不强校验**（不改现有入库单"全可空零联动"行为）。
- **染色环节**：数据来自进度反馈覆盖层（外发黑盒手动代录，ADR-0031），其余环节从执行单据与流水自动聚合。
- **预警（ProgressAlert）三条**：① 临期（交期 ≤7 天且未发完）② 超期（交期已过且未发完）③ 延期缸（该合同染色单下存在延期反馈缸）。排产超量等规则后置。

### 4. 性能：实时批量聚合，无物化

`page` 按页内合同 ID 集合逐环节批量聚合（IN + GROUP BY，避免逐合同 N+1），不做定时任务、物化表或缓存；数据量上来后再优化。

## 后果

- 进度永远等于下游执行数据的和，不存在第二套口径；新增消费方（看板、客户门户）直接复用查询服务。
- 每次查询都要多层 join + 聚合，页级延迟随数据增长劣化——是"零迁移+口径统一"换来的已知代价，优化路径（物化/缓存）已预留且不影响口径。
- 错误码预留 `1-030-019` 段（只读查询，预计极少）。
