# ADR-0029：发货单即出库凭证，三态严格过账（审核=出库写负流水、取消=红冲）

**状态**：Accepted
**日期**：2026-09-27
**关联**：业务管理-发货管理 MVP；镜像 ADR-0016（入库过账）、ADR-0017（通用库存流水）

## 背景

旧系统（linaagi）的发货域模型沉重：`Shipment` 有 PENDING_APPROVAL/DRAFT/PENDING/STAGED/SHIPPED/DELIVERED/REJECTED/CANCELLED 等多态，审批通过后经 outbox 异步执行 5 步副作用（来源库存标记已发、应收台账、订单进度、客户画像、通知），并有 STAGED 预出库 + 拣货扫码锁卷机制。

新项目做发货 MVP 时必须回答：发货与"出库"是什么关系？沿用多态审批链还是对齐新系统已有的入库单模型？

## 决策

1. **发货单即出库凭证**：不另建销售出库单，不引入"发货通知单→拣货单→出库单"多单结构。审核（发货）即在同一事务写库存负流水；未来采购退货、调拨、其他出库再建通用出库域。
2. **三态严格状态机**（镜像 ADR-0016）：
   - `DRAFT` 草稿（新建缺省）：可编辑、可删除、可审核；
   - `COMPLETED` 已发货：审核同事务过账后只读，唯一写操作是"取消"（红冲）；
   - `CANCELLED` 已取消：终态，只读。
3. **流水类型**：新增两个后端内部枚举（不入字典）`SHIPMENT_OUT`（审核，负数）/ `SHIPMENT_OUT_REVERSAL`（取消红冲，正数）。COMPLETED → CANCELLED 时按关联单号反查原流水逐条追加反向行，原流水不删不改。
4. **一单一仓库 + 不足硬拦截**：一张发货单只能选一个发货仓库；审核时按"物品+仓库"聚合校验可用余额，不足直接报错（返回需求量/可用量，仿领纱 YARN_OUT 先例），不允许负库存。
5. **制单与审核分权**：审核/红冲独立权限码 `lunaerp:business:shipment:audit`，打印独立 `:print`。
6. **上游零联动**：销售合同可选、客户必选；审核只写库存流水，不写应收、不回写合同状态/进度、不做发票关联。明细行可快照来源入库明细 ID（仅存在性校验，零回写）。

## 理由

1. 发货与入库是同一库存账的镜像两面：入库单已是"凭证即过账"的成功标杆，镜像设计使概念最少、账理最直，旧系统 5 步副作用链中的"库存同步"在新模型里就是过账本身，无需 outbox。
2. 库存即资金：超库存发货与负库存意味着账面错货，硬拦截把"改量还是分批"的决定权留给人，而不是让系统默默透支。
3. 应收/发票/合同进度等下游域在新项目尚不存在；发货流水已携带物品、仓库、合同关联，未来任何只读聚合（如合同发货进度）随时可算，不必提前建联动。
4. 不沿用旧系统多态：审批流、STAGED 预出库、拣货锁卷都依赖更重的流程与卷级库存身份，与 MVP "先跑通核心库存账"的目标不匹配。

## 考虑过的备选

- **新建通用"出库单"域，发货单仅作为其一种来源**：模型更"正统"，但 MVP 只有销售发货一种出库场景，提前抽象只增加空壳层。否决；该路径不封死，未来可由出库域收纳发货。
- **沿用旧系统多态 + 审批 + STAGED**：功能全但模型沉重，且新系统无卷级档案、无审批引擎，锁卷无数据基础。否决。
- **不足时软警告、允许过账**：操作顺滑，但负库存污染库存账且事后难追责。否决。

## 后果

- 发货单 Service 的 update/delete/audit/cancel 全部带状态守卫，错误码段 `1-030-016-xxx`。
- 库存流水新增 SHIPMENT_OUT / SHIPMENT_OUT_REVERSAL 两个 txn_type，库存余额恒等于流水 SUM，发货审核后对应物品仓库余额实时减少。
- 未来引入审批流可在 DRAFT→COMPLETED 之间插入审批态；电子签收（H5/token/签名）、预出库锁库作为后续增量，不推翻三态主结构。
