# ADR-0046：销售归属链接通行级数据范围——4 档收口、联系人零列继承、调岗同事务刷归属部门

**状态**：Accepted
**日期**：2026-10-08
**关联**：wayfinder 21-data-permission-wiring grilling（Q1–Q18）；spec `.scratch/data-permission-wiring/spec.md`；16 号商业化验收 spec §6.2（4 档走查）/§6.3（越权矩阵）；ADR-0004（编号含软删全租户唯一，决定取号扫描必须关闭数据权限）；ADR-0034（生产进度只读聚合）

## 背景

芋道底座自带 5 档数据范围（全部/自定义部门/本部门/本部门及以下/本人），机制为 MP 拦截器按注册表名拼 `(dept_id IN (...) OR user_id=?)`，多角色取并集。商业化一期只需要 4 档，且只给**销售归属链 5 表**（客户、客户联系人、报价单、销售合同、发货单）接通行级可见性。三条事实约束了设计：

1. 5 表中合同/发货已有 `salesperson_user_id`（可空、可改），客户/联系人零归属列；联系人是客户的子资源（ADR-0002 独立 controller 子资源），没有独立销售资产语义。
2. 底座源码注释明示芋道默认方案是 dept 列**快照不随调岗修改**；而 16 号验收 §6.2 的换岗用例要求"旧归属数据按新规则**立即**变化"，两者直接冲突。
3. 底座同时改写 SELECT/UPDATE/DELETE 与子查询，且有一批系统侧查询天然要求"租户内全量"（编号取号含软删、未发量聚合、审批回写、财务过账、回收站），一旦注册表被规则覆盖就会被静默加条件——少发条件的方向不是越权而是业务错误（重号、虚假未发量、漏过账）。

## 决策

1. **列模型：4 张持单/档案表统一 `salesperson_user_id` + `dept_id`，联系人零列。** 不新造 `owner_user_id` 命名（合同/发货列名不动，零迁移成本），"归属人=归属业务员"一词到底。`dept_id` 永远由后端按最终归属人当前部门推导，不接受前端入参；归属人可空，空归属行仅"全部"档可见。
2. **客户联系人实时继承客户归属**：联系人表不加列、不注册规则；列表用 EXISTS 子查询（拦截器深入子查询给 customer 表加条件），详情/写操作先做客户可见性校验，不可见统一回答"客户联系人不存在"。
3. **调岗同事务刷列**：lunaerp 切面拦截 system 用户更新，dept_id 变化时同事务把该用户名下 4 表的 `dept_id` 刷为新部门（owner 列不动，SELF 档不受调岗影响）；另附幂等校正 SQL 供排障。**不采用**底座快照默认，以满足验收 §6.2 的即时可见性。
4. **5 档收敛为 4 档但底座代码不删**：字典 id=35 与枚举 `DEPT_CUSTOM`/计算分支保留（升级兼容、存量库瞬时存在 2）；收口做在三处——前端角色弹窗白名单过滤 value=2、后端 `assignRoleDataScope` 拒绝 2（system 错误码 1_002_002_006）、存量 common→SELF / test-dp→ALL 迁移。
5. **"用户侧开启、系统侧关闭"成为后续模块契约**：取号扫描（ADR-0004）、未发量/进度聚合（ADR-0034）、审批回写、财务过账、回收站、删除引用守卫的 Service 方法显式 `@DataPermission(enable=false)`；关闭数据权限不影响租户拦截器。
6. **带单归属只向前继承一次**：报价→合同、合同→发货预填 owner，dept_id 服务端重算；之后各自独立，客户/合同改归属不回刷下游，联系人是唯一的实时继承例外。
7. **部分索引双列护航性能**：每表 `(tenant_id, dept_id)` 与 `(tenant_id, salesperson_user_id) WHERE deleted=0` 两个部分索引，受限档 BitmapOr，ALL 档零影响；万行 P95<1s 写入验收 perf 脚本。

## 理由

1. **单一事实源原则**：联系人的归属在业务上没有独立于客户的生命周期。自挂两列必然带来"客户转归属时级联刷联系人"的同步义务与不一致窗口；EXISTS 继承零冗余、零同步，代价仅是一条子查询，而该子查询恰好走新索引。
2. **验收基准不可让位于框架默认**：芋道快照方案在"主管查看在制销售资产"的场景下给出反直觉结果（调岗后旧主管仍见、新主管不见），而商业化验收明确选择了"组织视角实时"。同事务切面把一致性写进用户更新事务，读路径零额外成本；风险（调岗频次极低、更新走 `(tenant_id, salesperson_user_id)` 索引）远小于改验收口径或引入异步对账。
3. **裁剪而非分叉**：自定义档的 90% 复杂度（角色-部门关联表、PermissionServiceImpl 分支）留在底座里但不可达——UI 不可选、API 拒绝、存量迁移，三道闸门使该档在产品上消失，同时底座升级不产生冲突。真删枚举/字典/分支则是对底座的侵入式分叉，且存量库可能瞬时存在 data_scope=2 的行。
4. **系统侧显式关闭优于"恰好有权限"**：未发量聚合若只依赖"当前用户是 ALL 档"，未来任何一个新角色/新入口都会把它变成超发事故。把关闭意图标注在方法上，是把正确性绑定到代码而不是组织配置；这与租户拦截器的既有纪律一致（系统扫描点已有显式口径）。
5. **命名与列复用消除概念税**：owner_user_id 与 salesperson_user_id 并存会让 spec、测试、培训长期解释"两种归属人"；归属业务员本就是销售链归属的业务含义，统一命名后规则注册、GLOSSARY、权限文案全部一词到底。
6. **不回刷下游避免写风暴**：归属是建档时点的事实，单据一旦带单生成即独立承担其可见性（发货跟合同走而非跟客户走，符合业务上"谁跟单谁负责"）；实时级联回刷会让一次客户改归属变成跨 3 表批量写并产生审计解释成本。

## 考虑过的备选

- **联系人自挂 owner/dept 两列**：列表过滤简单，但客户改归属需级联刷联系人，且联系人可被转交归属造成与客户脱节的怪状态。否决，联系人继承客户。
- **沿用芋道调岗快照默认**：零代码，但与验收 §6.2"换岗立即变化"冲突，需回头改验收口径；且快照语义对销售主管视图不友好。否决，选切面同步；快照方案保留为"归属校正 SQL"可手动回到任意口径的退路。
- **PG 触发器同步 dept_id**：对读侧透明，但跨模块知识藏进数据库、团队既有规则全在 Java 侧、租户上下文与测试环境一致性差。否决。
- **彻底删除自定义档枚举/字典/底座分支**：分叉底座、升级冲突、存量 2 值行无兜底。否决，保留代码、产品层三闸收口。
- **统一改名为 `owner_user_id` 并迁移合同/发货旧列**：命名更抽象，但 4 表 ALTER+全栈字段改名纯成本无收益。否决。
- **dept_id 由前端表单带入**：可伪造他人部门归属，越权面直接打开。否决，服务端按归属人推导是硬约束（与既有"不信任前端身份字段"经验一致）。
