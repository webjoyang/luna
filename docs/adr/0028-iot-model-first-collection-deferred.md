# ADR-0028：IoT 模型与展示先行、真实采集后置——三表 + LoomDataCollector 接口

**状态**：Accepted
**日期**：2026-09-25
**关联**：生产管理-织造执行；ADR（织机档案随 0023 定义）

## 背景

参考系统 IoT 由三层组成：

1. **厂商凭证**（`VendorCredential`）：每客户/采购批次一组厂商 API 账号，密码只存加密值；
2. **设备绑定**（`DeviceBinding`）：厂商设备 → 本系统织机的归属映射，防跨租户污染；
3. **实时快照**（`MachineRealtime`）：定时从厂商 API（ZX23-YJ 协议）拉取的最新设备值。

真实对接的阻塞点不在代码侧：需要厂商 API 文档、有效凭证、车间网络可达与定时任务窗口。
在没有真实设备可验证时全量写采集实现，代码无法验证也容易返工。

## 决策

### 1. 三表全部落库（模型先行）

- 厂商凭证：`vendor_account`（租户内唯一）、`vendor_password_enc`（**加密存储，禁止明文**，
  复用项目已有加密能力）、`scope`、`status`、`last_sync_at`。
- 设备绑定：`vendor_device_id`（厂商侧唯一标识）、`loom_id`（绑定本系统织机）、`status`、`last_sync_at`；
  归属以绑定表为权威路由。旧系统的 workshop_id 不迁移（项目尚无车间实体）。
- 实时快照：`(tenant_id, vendor_device_id)` 唯一；字段含 `status`
  （running/idle/abnormal/disabled/offline）、效率、分钟圈速、班次圈数、限制圈速、
  运转分钟、在班分钟、在班人员、设备编号、`fetched_at`。

落点：后端 `production.iot` 子包；前端不单独开菜单——凭证/绑定管理与快照查看作为**织机档案页内 Tab**。

### 2. 采集层接口抽象 + 模拟实现（采集后置）

- 定义 `LoomDataCollector` 接口：按凭证拉取设备清单与最新快照，输出统一的快照对象；
- 本期提供：**手工录入快照端点**（管理员按设备维护）与**模拟采集实现**（可按绑定关系生成模拟值），
  不启用真实定时任务；
- 真实厂商适配 + 定时调度待协议/凭证/现场网络就绪后作为独立任务补，接口不变则上层（快照表、展示）无需改动。

### 3. 信息源不互相污染

- IoT 快照**不回写**织机档案 `status`——织机状态由人工维护（启用/停用），
  快照表达设备实时运行情况；列表/看板以快照为辅助列并列展示，两个口径不合并。
- 快照只保留最新值（更新覆盖），不做设备历史时序表——历史趋势待真实采集上线后另行设计。

## 后果

- 本期交付后，设备数据可手工/模拟流转，织机页具备展示位与绑定关系；真实对接是新增一个 Collector 实现 + 一个定时任务，不动数据模型。
- 密码加密、租户隔离、归属路由三条安全约束在模型阶段即固化，真实对接时不得绕开。
- 风险：若厂商协议字段与现快照模型差异很大，未来可能需要加列；快照列均可空，加列成本低，可接受。
