# ADR-0030：发货卷清单独立子表（聚合明细行 + 行内卷记录，随单聚合保存）

**状态**：Accepted
**日期**：2026-09-27
**关联**：业务管理-发货管理 MVP；刻意不同于旧系统 rollDetails JSON

## 背景

发货业务需要回答两个层面的问题：
1. **按品种/缸号**：这批发了什么货、各多少数量/匹数、多少钱——聚合口径；
2. **按卷**：具体发出了哪几卷、每卷实称重量多少——实物追溯与装箱单口径。

旧系统（linaagi）把卷信息以 `rollDetails` JSON 字符串（卷号+重量+备注）存在 `ShipmentItem` 行内，另有独立的拣货扫码表（ShipmentPickRecord）承担锁卷。新项目没有卷级库存档案，需要决定卷数据的承载方式与校验强度。

## 决策

1. **两级模型**：
   - `发货明细 (ShipmentItem)`：按产品+客户色号+缸号聚合的行，记载数量/匹数/单位/单价/金额；
   - `卷清单 (ShipmentRoll)`：**独立子表**，挂在明细行下，逐卷记录卷号、实称重量（KG）、米数、备注。
2. **随单聚合保存**：卷清单没有独立端点与权限码，随发货单整体保存、级联逻辑删除（ADR-0003 聚合模式）；仅主表有 Controller。
3. **不强制齐套**：不校验卷重合计等于明细行数量，允许零卷清单审核；前端仅软提示"已录卷重 X / 行数量 Y"。过账数量以明细行为准。
4. **不锁卷、不校验卷归属**：卷清单只是发货事实的留痕与打印装箱单的数据源，不回写任何库存状态、不占用在库卷。

## 理由

1. **独立表优于行内 JSON**：卷记录需要按卷查询、跨明细行平铺成装箱单、支持打印与未来可能的卷级追溯；关系子表可直接分页/关联/聚合，JSON 字段在 SQL 侧难以索引与统计。这是与旧系统的刻意不同。
2. **不做卷级选择/锁库是数据基础决定的**：新系统库存是"物品+仓库"聚合余额、批次号仅为自由文本，没有卷身份档案，从库存勾选具体卷无从谈起；卷号由发货时人工录入/扫码填入即可。
3. **软校验贴合现场**：散匹、拼卷、先开单后补卷号是常态，强齐套会挡住正常单据；卷清单缺失不影响库存账（账以明细行为准）。

## 考虑过的备选

- **沿用 rollDetails JSON 存行内**：与旧系统一致、迁移直观，但统计/打印/查询需在应用层反复解析 JSON，且无法加约束。否决。
- **每卷一行作为发货明细（卷级明细）**：粒度最细，但要求从在库卷中勾选，新系统无卷档案；且聚合金额、按缸号汇总反而需要二次合并。否决。
- **完整复刻 STAGED + 拣货扫码 + 卷状态占用**：锁库防重发是其价值，但依赖卷级身份与预出库流程，超出 MVP 范围。否决。

## 后果

- 建表 `lunaerp_business_shipment_roll`，外键关系为逻辑关联（shipment_item_id 列，不建数据库外键，对齐项目惯例）。
- 前端发货明细 Tab 行内弹窗维护卷清单，另有"卷清单总览"Tab 跨明细行平铺全部卷，作为装箱清单打印数据源。
- 未来如建立卷级库存档案/预出库锁库，卷清单可扩展关联卷 ID，但表结构无需推翻。
