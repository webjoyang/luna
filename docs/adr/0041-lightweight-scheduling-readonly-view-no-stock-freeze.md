# ADR-0041：轻量排产与齐套——只读视图 + 既有实体校验，不建排产表/染缸台账/库存冻结

**状态**：Accepted
**日期**：2026-10-07
**关联**：轻量排产与齐套检查（`.scratch/scheduling-material-check/spec.md`，lunaerp 商业化 issue 09）；ADR-0034（生产进度只读聚合）、ADR-0024（织造布票/机台任务状态推导）、ADR-0017（通用库存流水台账）、ADR-0027（领纱发纱与冲销）、ADR-0031（染色进度反馈覆盖层）；charting Q10=A（规则计算，不做 AI 优化排程）

## 背景

车间排产与开工前齐套检查是 W2 链路（合同→下达生产→织造/染色→入库发货）的最后一块缺口。设计时面对三个"要不要建实体"的选择：

1. **织造排产**：现有机台任务 `lunaerp_production_machine_task` 已记录机台、计划起止日期（天粒度可空）、计划匹数与四态（ADR-0024），但只能从织造单工作台逐单维护，无跨单视图，且创建/更新只有 `end ≥ start` 校验，同织机时段重叠不拦截。常规 ERP 的做法是另建"排产计划/派工单"实体（独立编号、状态机、版本）。
2. **染缸排缸**：染色全部外发，缸是染厂资源；现有进度反馈覆盖层（ADR-0031）的反馈缸已记录缸号、排缸日、六态、数量。常规做法是建本厂"染缸设备台账 + 排缸占用表"。
3. **齐套检查**：台账余额（ADR-0017）、配比 BOM（ADR-0011）、领纱测算口径（ADR-0027）已就绪。常规做法是建齐套检查表留档，并对缺料做"库存预留/冻结"，让排产锁定库存。

经对老系统（linaagi）核实：`DyeingVat` 同样是缸次记录而非设备台账；老系统织造侧的 MachineGanttBoard 也是直接在 MachineTask 上派工，两代系统都不存在独立排产实体。

## 决策

### 1. 织造排产 = 现有机台任务上的查询视图层 + Service 冲突校验层，零新表零加列

- 不建排产单/排产计划/版本表。排产中心（甘特、待排池、跨单列表）全部是对机台任务、织机、织造单的实时只读查询组装。
- 在 `MachineTaskService#create/update` 增加**同织机计划时段闭区间相交硬拦截**：同 `loom_id`、状态 ∈ PENDING/IN_PROGRESS/HALTED、日期相交（同日即冲突）的他任务存在即报错（`1_030_036_000`）；COMPLETED 历史区间豁免，无日期任务不占时段（进待排池）。存量重叠数据不回刷，以甘特冲突红标呈现。
- 冲突校验两端入口（织造单工作台、排产中心）共用同一 Service，不设旁路。

### 2. 不做数据库排他约束，接受极端并发下的双占窗口

Postgres EXCLUDE（btree_gist + daterange）可严格防重叠，但依赖扩展（私有化环境不可控）、谓词需处理可空日期/软删/COMPLETED 豁免，而排产是低频写（单厂每天数十次）。一期以应用层先查后写为准，极端并发双占由甘特红标 + 人工改期兜底。

### 3. 不建染缸设备台账；排缸日历是进度反馈的视图切换

外发模式下本厂不拥有染缸，设备台账业务不成立；排缸所需字段反馈缸表已全有。排缸日历不单独建表/菜单/权限，仅在进度反馈页内新增月历只读视图，改期复用反馈缸更新接口。

### 4. 齐套检查是时点只读试算，不落表、不冻结库存

- 需求口径复用领纱测算：织造单计划重量 × 配比 ratio/100，按纱线规格聚合；可用量取台账实时余额（YARN_OUT 已实时扣减，不重复扣"已领"）。
- 在途纱线 = ACTIVE 纱线采购单明细实采量合计（入库单不关联采购单，部分到货无法核销，为已知近似口径）。
- 不建齐套检查表、不预留/冻结库存、不自动生成采购单。建议采购量仅作页面数值与跳转参考。

### 5. 排产状态全部派生，织造单状态机零改动

不加"已排产"字段；未排/部分排/已排满/生产中/已完工由任务实时聚合派生。机台任务完成→布票推导→织造单推进（ADR-0024）链路不变，排产模块对生产单据零回写，延续 ADR-0034 的"投影不是表"边界。

## 备选方案与否决理由

- **独立排产计划实体（独立编号/状态机/版本）**：与机台任务形成两套"机台×时段"事实源，状态互推复杂；当前规模（单厂几十台织机、天粒度、工长手工排）不需要版本化排程。
- **染缸设备台账 + 排缸占用表**：染色外发，设备归属染厂；本厂维护染厂设备产能数据既不可得也无意义。
- **库存预留/冻结表（排产锁料）**：需要"占用→释放/扣减"的完整生命周期与所有异常分支（改期、删任务、订单取消），与台账流水模型（ADR-0017）叠加双口径；一期齐套的价值是"看得见缺口"，不是"锁得住库存"。
- **dhtmlx-gantt**：虽随芋道底座已在 node_modules，但其社区版为 GPL v2，与一期私有化商业化买断的发布方式冲突；选用 MIT 的 vue-ganttastic。
- **AI 优化排程**：charting Q10=A 已排除，写入非目标。

## 后果

- **正面**：零数据迁移、零状态机风险；排产/齐套/日历全部随既有数据实时反映，口径单一（机台任务是唯一的机台占用事实源，台账是唯一库存事实源）；交付面集中在查询接口与前端看板，可在一个迭代内完成。
- **代价**：
  - 应用层冲突校验存在并发双占窗口（低频、可观察、可人工纠正）；
  - 齐套不锁库存，试算后被领/被采不会通知，需用户自行及时复核；
  - 在途是采购单状态近似值，依赖人工及时完结采购单，部分到货期间会高估在途；
  - 甘特能力受开源轻量库边界约束（如跨行拖拽不稳则降级为弹窗转机）。
- **二期路径**：若多厂协同/高频插单成为常态，再升级为独立排产实体 + 排他约束 + 产能日历；若采购链深化（入库单↔采购单核销），在途口径可替换为精确未到货量；库存冻结随 MES 级执行需求再评估。三者均不影响一期 schema（因为一期没有需要废弃的表）。
