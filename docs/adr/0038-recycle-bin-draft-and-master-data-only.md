# ADR-0038：统一回收站只收主数据与草稿单据，恢复不补账

**状态**：Accepted
**日期**：2026-10-07
**关联**：W0 商业地基通用件（`.scratch/common-foundation/spec.md`）；ADR-0016（入库过账状态机）、ADR-0017（通用库存流水台账）；统一 DoD"列表/详情/删除进回收站"

## 背景

商业化统一 DoD 要求各模块删除可进回收站、可恢复。一种自然的朴素理解是"所有删掉的单据都进回收站，恢复时链式补回库存和账务"。但新栈已有两条既定约束使该理解不成立：

1. **已过账单据不可删除**（ADR-0016）：入库单等严格状态机下，COMPLETED 单据的唯一逆向操作是"取消"——按 ADR-0017 追加反向流水（如 `STOCK_IN_REVERSAL` 负数行）红冲，原流水只增不改不删，单据本身保留为 CANCELLED，不从列表消失。
2. **全表逻辑删除**（shared GLOSSARY"软删除"）：所有表有 `deleted` 列，实际删除路径只对 DRAFT 草稿与主数据开放（如 `StockInServiceImpl#deleteStockIn` 仅草稿态放行，删除时级联软删明细/放置记录）。

因此需要明确回收站的收纳边界、恢复语义与实现形态，避免后续模块 ticket 各自解释"恢复要不要补账"。

## 决策

建**零新表**的统一回收站机制，边界如下：

1. **收纳范围**：主数据（客户/供应商/产品/纱线材质/纱线规格）与**仅 DRAFT 状态**的草稿单据。回收站查询 = 各模块 `RecycleBinHandler` 用手写 SQL 显式查 `deleted = 1`（MyBatis Plus 逻辑删除的刻意反向使用），不建回收站快照表。
2. **已审核/已生效单据永不进回收站**：它们的逆向操作是红冲取消（CANCELLED 留痕），是业务动作而非删除；回收站 UI 与 API 对这类对象不注册 handler。
3. **恢复不补账**：回收站里的数据从未产生过库存/账务副作用（草稿不写流水、主数据不记账），恢复只做 `deleted=0` 复活与级联子表父→子复活，不触碰任何台账/分录账。"链式补回"一词在本栈仅指级联软删子行的复活，不指账目。
4. **恢复后状态**：主数据恢复为 INACTIVE（沿用删除前置 INACTIVE 惯例），需手动启用；草稿单据恢复为 DRAFT。
5. **引用阻断**：草稿引用的主数据（或子对象引用的父对象）仍在回收站时，阻断恢复并提示恢复顺序；编号唯一索引含已删行，复活原行不产生重号。
6. **彻底删除**：提供物理删除（独立权限），主数据存在有效业务引用时禁止；不做自动清空。

## 理由

1. **账实一致性**：若允许已过账单据"删除→恢复→补账"，就要在恢复路径重放审核过账，而期间库存可能已被后续单据消耗、价格/汇率快照可能已变，重放必然失败或造假账。红冲+重新制单是唯一可审计路径（ADR-0016/0017 已论证）。
2. **零新表**：删除行本身就是最完整的快照（带 updater/update_time），再建 recycle_record 表需要侵入所有删单路径双写，且快照与真实行漂移后恢复语义更混乱。Handler SPI + 注册表把成本放在各模块一次实现，回收站核心零数据模型。
3. **主数据恢复为 INACTIVE 而非原状态**：删除期间该主数据对业务不可见，引用关系可能已变化（如草稿被他人恢复前重建了同名档案由唯一索引拦截外的情形），恢复为停用态强制人工确认后再启用，避免"恢复即参与业务"。
4. **手写 SQL 查 deleted=1**：MP 逻辑删除自动改写所有内置查询，只有自定义 XML 可精确表达回收站语义；附带的代价是租户条件也要手写，故 ADR 明确要求租户条件入 SQL 并有隔离测试守护。

## 考虑过的备选

- **所有删除单据进回收站（含已审核），恢复时重放过账补回库存/账务**：恢复路径等价于重新审核，无法处理库存已被后续业务占用、快照过期、红冲已发生等情形，且会产生"同一单据两次入账"的审计漏洞。否决。
- **新建 `lunaerp_recycle_record` 快照表**：删除时双写名称/删除人/时间，可跨类型混排。但快照与真实行漂移、所有删单路径要改造、恢复仍要回各表 UPDATE，收益仅省掉各模块一个查询 SQL。否决。
- **恢复主数据直接还原原状态 ACTIVE**：缺少人工确认环节，停用态成本极低而误恢复代价高。否决。
- **不提供彻底删除，数据永久保留**：私有化交付客户有数据清理诉求（误建测试数据），物理删除有引用守卫足够安全；自动/批量清理风险高故不做，但单条受控保留。

## 后果

- 回收站是"软删行的浏览器"，不是一套独立生命周期；所有可删对象必须是 DRAFT/主数据，这反过来约束各模块状态机：**需要删除的单据必须有 DRAFT 态**。
- 各业务模块 spec 必须声明自己的 `RecycleBinHandler`（统一 DoD）；红冲类单据明确不注册。
- 已审核单据的"反悔"操作一律走"取消（红冲）→ 重新制单"，培训与 UI 文案需区分**删除（进回收站）**与**取消（红冲留痕）**两个动作。
- 若未来出现"删除已生效档案"（如停用后清理客户）的合规需求，只能走彻底删除或匿名化，不经过恢复路径。
