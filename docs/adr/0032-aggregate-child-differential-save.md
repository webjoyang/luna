# ADR-0032：聚合子表按行 ID 差异保存（取代"先删后插"）

**状态**：Accepted
**日期**：2026-09-28
**关联**：**supersedes ADR-0003 中"对子表先删后插"的持久化机制**（聚合边界不变——无独立端点、整表提交、同事务保存、级联逻辑删除）；ADR-0031 进度反馈覆盖层的前置依赖

## 背景

lunaerp 七个"主表 + 聚合子表"单据，更新主表时对子表的处理全部是"按父 ID 删除全部旧行 + 批量插入本次提交行"：

| 聚合 | 子表 |
|---|---|
| 销售合同 | SalesContractItem |
| 染色单 | DyeingColor |
| 胚布单 | GreigeOrderColor |
| 纱线采购单 | YarnOrderItem |
| 发货单 | ShipmentItem + ShipmentRoll（卷挂明细行） |
| 入库单 | StockInItem + StockInItemPlacement（放置挂明细行） |
| 纱线配比 BOM | YarnRecipeBomItem |

进度反馈覆盖层（ADR-0031）需要持有稳定的 `dyeingColorId` 作为关联键，而"先删后插"使染色颜色行每保存一次就换一批 ID，外部关联必然悬挂。盘点同时发现：四个子表的 SaveReqVO 连 `id` 字段都没有，发货/入库子表虽有 `id` 字段但前端编辑时以数组索引维护行、不回传 ID。

## 决策

1. **七个聚合的全部子表统一改为按行 ID 差异保存**。子表 SaveReqVO 携带可空 `id`；同事务内对本次载荷与库内存量做差集：
   - 提交带 `id` 且库内存在 → `updateById`；
   - 提交无 `id` → insert；
   - 库内存在但本次未提交 → 逻辑删除（`deleted=1`，沿用软删除机制）；
   - `lineNo` 每次保存按提交顺序统一重排。
2. **聚合内部两级子表按"先父行、后子行"差异保存**（发货卷→发货明细、入库库位放置→入库明细）：未变更父行的 ID 保持不变，子行关联不悬空；提交中子行引用了本次被删父行 ID 时报校验错误（防御性，正常前端路径不可达）。
3. **跨聚合引用做硬守卫**：染色单更新时，被移除的颜色行下若存在反馈缸，报错拦截（1-030-017-004），引导先删缸反馈。其余六个子表当前无跨聚合引用，移除即正常差异删除。
4. **前端七个编辑页联动**：加载详情时保留每行后端 ID，编辑过程中以行 ID 为身份（而非数组索引），提交时原样回传。
5. **适用边界**：本约定针对上述七个业务单据聚合及未来新增的同类聚合子表。产品图片（ProductImage）这类无任何外部引用的纯附件子表不在范围内——差异保存零收益且多一处回归面。
6. **验证要求**：每个模块 ServiceImpl 单测（Mockito、不连数据库，沿用发货管理测试先例）必须覆盖四条更新路径：未变更行 ID 不变、修改行走 update、移除行走逻辑删除、新增行走 insert；前端七页逐一回归"改单后行数据不串、关联数据不丢"。

## 理由

1. **行身份稳定正在成为刚需**：进度反馈是第一个跨聚合引用聚合子表行 ID 的功能，但不会是最后一个（合同行级发货/开票在 ADR-0003 中已被预见）。统一改造七个聚合，避免未来每出现一个引用方就打一次补丁，也避免"为什么只有染色单特殊"的长期认知负担。
2. **"先删后插"的收益只是实现简单，成本是隐形的**：除外部关联悬挂外，还导致行审计字段（creator/create_time）每次保存全部刷新、前端无法用行 ID 做稳定 key 与局部交互、逻辑删除表中堆积无意义的行尸。差异保存把语义从"替换整个集合"纠正为"用户在表单里实际做的增改删"。
3. **聚合边界不因保存机制而改变**：ADR-0003 确立的"无独立 Controller、整表载荷提交、同事务、随主表级联删除、汇总字段服务端重算"全部保留——差异保存只是事务内的写入方式，不引入逐行端点与独立权限码。
4. **硬守卫优于失效标记**：被引用行允许删除会产生永久孤儿数据，覆盖层查询与统计要无限期兼容残行；而删除缸反馈本身随时可做且不影响染色单，用户路径通畅，拦截不构成业务阻塞。

## 考虑过的备选

- **只改造染色单颜色明细**：进度反馈的最小成本路径，但与其余六个聚合长期刻意不一致，且"聚合行 ID 是否稳定"将变成需要逐模块记忆的隐性知识。用户选择统一改造。
- **保持先删后插，覆盖层改用业务文本键 JOIN**（linaagi 模式）：规避改造但继承文本键漂移问题，颜色改名即产生悬挂/错配。否决。
- **逻辑外键 + 数据库级约束/级联**：项目惯例不建数据库外键，删除守卫统一在 service 层，沿用之。

## 后果

- ADR-0003 的聚合保存结论继续有效，但其中"按 `contract_id` 先删后插"的机制描述以本 ADR 为准（已在 ADR-0003 补注）。
- 七个模块的后端（SaveReqVO/Mapper 的 selectIds/deleteByIds/ServiceImpl）与前端七个编辑页需要联动修改并全量回归；作为独立的"阶段一"工程治理先行交付，不夹带任何业务语义变化。
- 差异计算依赖前端回传正确的行 ID；旧前端页面若漏改，保存行为会退化为"全部新增 + 旧行全删"，因此阶段一的回归以"未改行 ID 不变"为验收锚点。
