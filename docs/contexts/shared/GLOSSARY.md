# 跨域共享约定（shared）

本文件收录 Luna ERP **跨所有业务域**的平台约定与共享词汇：多租户、软删除、前后端模块结构约定、错误码段位分配总表。
任何业务域（baseinfo / business / production / stock / sample / finance）的工作开始前都应先读本文件。各业务域自己的术语见根目录 `GLOSSARY-MAP.md` 指路的各域 GLOSSARY.md。

## 多租户

**租户 (Tenant)**：
多租户通过后端 `TenantBaseDO` 强制（自动注入 `tenant_id` 列、自动过滤查询）。lunaerp 各域主表与子表（如 Customer/CustomerContact、Supplier/SupplierContact 等）都继承 `TenantBaseDO`。

## 软删除

**软删除 (Soft delete)**：
记录通过 `BaseDO`/`TenantBaseDO` 继承的 `deleted` int2 列做逻辑删除，查询自动过滤 `deleted = 0`。客户与供应商删除时 service 层都先置 `status = 'INACTIVE'` 再走逻辑删除（与 product 模块模式一致），便于忽略 `deleted` 的审计/列表查询仍能看到生命周期变化。业务编号（供应商编号、合同编号、胚布单号、发货单号等）的唯一索引与取号扫描显式包含已删除行，软删后编号不释放、不重用——这是该过滤机制的刻意例外（各编号规则见对应业务域 GLOSSARY.md 与 ADR-0004/0005/0006/0029）。软删行的统一查看/恢复入口（回收站）及其"不含已过账单据、恢复不补账"边界见下文"统一回收站"与 ADR-0038。

## 前后端模块结构约定

**仓库双项目结构**：根目录并列两个项目——`luna-srv`（后端：Spring Boot + PostgreSQL + MyBatis Plus + Redis）与 `luna-ui`（前端：Vue3 + TypeScript + Element Plus）。一个业务域横跨前后端，领域文档统一放在仓库级的 `docs/contexts/<域>/`，不嵌入任一项目内部。

**后端包约定**：lunaerp 业务代码落在 `luna-srv/lunasrv-module-lunaerp`，按"层 → 业务域 → 子模块"组织：`com.luna.lunasrv.module.lunaerp.{controller,service,dal.*}.<域>.<子模块>`（controller 下无 `admin` 中间层；Mapper 包名历史为 `dal.mysql`，实际数据库为 PostgreSQL，沿用不改名），其中业务域固定六个：`baseinfo`（基本信息）、`business`（业务管理）、`production`（生产管理）、`stock`（库存管理）、`sample`（样品管理）、`finance`（财务，经营账；ADR-0037）。

**临时 UI 区 lunaerp-elmui**：
`luna-ui/src/views/lunaerp-elmui/` 是 `views/` 下的新目录，与既有的 `views/lunaerp/` 平级。它是一个**临时快速实现版**：用 Element Plus 快速搭出业务核心，先跑通前后端服务与关键流程。**未来 lunaerp 业务视图的正式 UI 仍然落到默认目录 `views/lunaerp/`**，`lunaerp-elmui/` 只承担"先行验证"的角色。详见 ADR-0001。产品信息等后建模块已直接落在正式目录 `views/lunaerp/`，各域具体落点以该域 GLOSSARY.md 的"模块边界"为准。

**冻结的借贷会计脚手架 `views/fms/`**：
`luna-ui/src/views/fms/`（凭证/账簿/三大报表/期末结转/账套科目）是无后端对应的纯前端脚手架，按 ADR-0037 **不迁后端、不挂菜单、不复活静态路由、代码原样保留**，不属于 finance 域；任何财务新功能进 `finance/` 目录，禁止挂接或改造 fms。

## 客户门户（横切）

**客户门户 (Customer portal)**：
面向外部客户的免登录 H5 触点（前端 `/portal/*` 路由区、后端 `/app-api/lunaerp/portal/**`），客户凭门户令牌查看**本客户名下**的发货单与对账单，并执行签收确认、对账单确认/驳回。数据边界=客户维度（不是租户维度）：同租户的不同客户互相不可见。一期最小集；供应商门户为二期（ADR-0044）。

**门户令牌 (Portal token)**：
业务员签发给客户的访问凭证，凭其恰好可访问该客户（含租户边界）名下的门户数据。每客户同一时刻仅一枚有效：重新生成即吊销旧链接、可手动吊销；128bit 随机不可枚举、有效期滑动。签收人/对账确认人由客户侧手填姓名，系统不建模"门户用户"。

**链接失效页 (Portal invalid page)**：
门户令牌无效/过期/被吊销时的统一着陆页，文案引导客户联系业务员重新获取链接；凭证失效的不同原因（伪造/过期/吊销）对外统一表现，不区分文案。

## 审批引擎（横切）

**审批链 (Approval chain)**：
按单据类型（`biz_type`）配置的固定审批流程，由多个节点按顺序组成。一期只支持固定链，不支持 BPMN 条件分支/子流程。每条链同一时刻仅一条启用。节点类型：逐级 / 或签 / 会签。

**逐级 (Sequential)**：
节点内单人审批，或多人按节点顺序串审（一期节点内只放一人，多人串审用多个节点实现）。

**或签 (Or-sign)**：
节点内任一审批人通过即节点通过；任一审批人驳回即节点驳回（一票否决）。先到先得，其余人的待办自动关闭。

**会签 (And-sign)**：
节点内全部审批人通过才节点通过；任一驳回即节点驳回（一票否决）。一期不做比例会签（如 2/3 通过）。

**审批实例 (Approval instance)**：
一次具体的审批流程执行，对应一张业务单据的一次提交。状态：`APPROVING`（审批中）/ `APPROVED`（已通过）/ `REJECTED`（已驳回）/ `CANCELLED`（已撤回）。发起时全流程节点与审批人解析快照存入实例，在途审批不受组织架构变动影响。驳回/撤回后修改再提交=新建实例，走全流程。

**审批任务 (Approval task)**：
实例中某个节点分配给某个审批人的待办。状态：`PENDING`（待处理）/ `DONE`（已处理，含通过/驳回/转交）。会签场景下同一节点生成多个 task，用 `version` 乐观锁防并发覆盖。

**审批操作记录 (Approval record)**：
审批实例上的每一次操作（提交/通过/驳回/转交/撤回）留痕，含操作人、意见、时间。是审计追溯的唯一来源，永不物理删除。

**approval_status（业务单据审批态）**：
加在需审批的业务单据主表上的跨切面字段：`PENDING`（草稿待提交）→ `APPROVING`（审批中）→ `APPROVED`（已通过）/ `REJECTED`（已驳回）/ `CANCELLED`（已撤回）。`APPROVED` 通过事件触发业务单据自身的生效/过账动作（审批引擎不直接写业务账目，对齐 ADR-0017）。非强制审批单据（如入库单/检验单）无此字段，沿用 ADR-0016 严格三态直接审核。

## 统一回收站（横切）

**回收站 (Recycle bin)**：
软删行（`deleted = 1`）的统一查看与恢复入口，零独立快照表，按业务对象类型经各模块注册的 handler（`RecycleBinHandler` SPI）查询。**只收纳主数据与 DRAFT 草稿单据**；已审核/已生效单据永不进回收站——它们的逆向动作是**取消（红冲）**，单据保留为 CANCELLED 留痕。边界与理由见 ADR-0038。未注册类型调接口报 1_030_031_000。

**恢复 (Restore)**：
将回收站记录 `deleted` 置回 0。主数据恢复后为 INACTIVE（需手动启用），草稿单据恢复为 DRAFT；级联软删的子表行按父→子顺序一并复活；引用的父对象（如草稿单据引用的客户，或纱线规格引用的纱线材质）仍在回收站时阻断恢复并提示恢复顺序（报 1_030_031_002）。**恢复不补任何库存/账务**——回收站中的数据从未记过账。恢复仅允许对 `deleted = 1` 行操作，重复恢复报 1_030_031_001。

**彻底删除 (Purge)**：
从回收站对软删行做物理删除（SQL 物理 `DELETE`），需独立权限（`lunaerp:common:recycle:purge`）；主数据仍被有效业务引用（`deleted = 0`）时禁止彻底删除（`hasActiveReference` 报 1_030_031_003）。草稿单据按聚合级联物理删除全部子表。一期逐条处理，不做自动清空与批量物理删除（防误操作）。

**删除 vs 取消 (Delete vs Cancel)**：
删除（Delete）的对象仅限草稿态单据与主数据，行进回收站（`deleted = 1`）、可恢复；取消（Cancel）的对象是已审核/已过账单据，走红冲追加反向流水（ADR-0016/0017），单据保留为 CANCELLED 终态，不可恢复为"未发生"，只能重新制单。UI 文案与培训必须严格区分这两个动作。
 
**软删恢复 vs 红冲取消 (Soft delete restore vs Reversal cancellation)**：
- **软删恢复**：基于逻辑删除列 `deleted` 的翻转（`deleted = 1 → 0`）。适用于草稿单据与主数据，因为这类数据在软删前从未参与过库存出入库台账记账或资金经营分录账记账，因此复活时只需恢复本行及级联子表数据，**不补账、不重放过账、不触碰台账**（ADR-0038）。
- **红冲取消**：基于会计与库存可审计性的反向对冲流水记录。适用于已生效/已审核过账单据。这类单据已在库内产生账务或实物流水副作用，绝不能被"逻辑删除进回收站"，更不能在"恢复"时试图重放过账（后续库存可能已被消耗或价格快照漂移）。唯一合法路径是追加红冲对冲单据/负数流水，单据行本身保留为 CANCELLED 终态永久留痕（ADR-0016/0017/0038）。

## 统一打印（横切）

**套打 (Fixed-template print)**：
按固定纸质版式（发货单、装箱清单、布票不干胶标签、对账单、出口单证）精确对位的前端打印，不提供模板设计器。统一机制为"公共打印内核（PrintDispatcher/PrintPaper/QrSlot/usePrintHtml） + 各模块就近模板 + 静态注册表（registry.ts）分发"；打印取数走独立 print-data 接口与打印 VO（打印件需要全量联系人字段，豁免脱敏），每次打印加 `@LogRecord` 写操作日志。布票/发货单上的二维码编码完整 URL（H5/门户基址走 infra_config），码格式为跨 ticket 冻结契约（见 `.scratch/common-foundation/spec.md`）。

## 固定敏感字段脱敏（横切）

**脱敏 (Desensitization / Masking)**：
敏感业务数据的权限条件掩码机制。通过自研 `@Sensitive(seePermission = "...", type = SensitiveType....)` 注解标在 RespVO 字段上，在 Jackson 序列化输出时根据当前登录用户是否持有对应权限位动态判定：持有权限输出原文，无权限或无登录上下文（如定时任务/MQ）输出脱敏掩码。底座已有姓名/手机/电话/银行卡/邮箱 5 种规则，新增 `AMOUNT` 金额脱敏规则（无权限输出 `"****"`，有权限输出数字/BigDecimal 原值）。全系统收敛为两个固定权限位：`lunaerp:sensitive:amount`（金额/成本/单价）与 `lunaerp:sensitive:contact`（联系人/手机/座机/银行卡/邮箱）。脱敏仅影响响应表现层，库内始终为明文；更新接口以 ID 为准且不接受脱敏值回写；Excel 导出同受脱敏约束；仅打印件走独立 print-data 接口予以豁免。

## 站内消息与待办角标（横切）

**站内消息 (Internal notification)**：
基于系统底座 notify 体系（`system_notify_template` 与 `system_notify_message`）的异步业务触达通知。零新增 lunaerp 业务表，封装 `LunaNotifyHelper.send(...)` 统一调用底座 API。单据审批流转（任务到达/通过/驳回）、合同生效、发货签收等关键节点触发发送；通知携带参数与跳转上下文（`bizType` / `bizId` / `bizNo`），点击可在前端自动路由至对应工作台或单据详情；通知发送失败仅记 error 日志，不回滚主业务事务。

**待办角标 (Todo badge)**：
系统全局顶部导航栏消息铃铛图标上的未读消息计数红点/角标。全系统保持**单个铃铛角标**统一收纳所有未读通知与待办提醒，不新建第二个角标或审批独立红点；审批待办数量仅在审批中心内部查询，保持系统交互一致与整洁。

## 数据范围与销售归属（横切）

**数据范围四档 (Four data scopes)**：
角色级行级可见性档位，一期商业化只开放四档：**全部**（租户内全量）/ **本部门及以下**（归属部门=本人部门及其子部门，并集本人名下）/ **本部门**（归属部门=本人部门，并集本人名下）/ **本人**（仅归属人=自己）。多角色取并集，任一启用角色为"全部"即见全量。底座原有的第五档**自定义部门**（指定任意部门集合）一期停用：UI 不可选、API 拒绝、存量角色迁移，底座枚举与字典保留不删。仅销售归属链 5 表接通，其余单据一期恒为全部档（ADR-0046）。

**归属人 (Owner / 归属业务员)**：
销售数据行的可见性锚点用户，列统一命名 `salesperson_user_id`，建档时缺省为建档人、可改；客户改归属不回刷其下游单据，带单（报价转合同、合同建发货）只向前继承一次。归属人为空的行仅"全部"档可见。

**归属部门 (Owner department)**：
归属人落库时点所属的部门，列统一命名 `dept_id`，由后端按归属人当前部门推导（不接受前端传入）。员工调岗时同事务批量刷新其名下各表归属部门，使"本部门"类档位的可见性随组织架构即时变化。

**客户联系人继承归属**：
客户联系人不持有自己的归属人/归属部门，其可见性始终实时继承所属客户：看不见客户就看不见（也探测不到）该客户的任何联系人。这是归属链上唯一的实时继承例外。
